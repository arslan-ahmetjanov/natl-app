# TestBlox — среда разработки UI-тестов поверх NATL

Черновик архитектуры на согласование. 13.11.2026.

## 1. Зачем это

Вайбкодинг поменял расстановку сил. Код пишет модель, читать его некому: основатель стартапа не ревьюит диффы, он смотрит, работает ли кнопка. Единственная проверка, которая остаётся, — поведение приложения.

Значит нужен инструмент, который превращает ручные клики в тесты, показывает, что произошло на каждом шаге, и отдаёт те же тесты в CI. Без YAML, без Playwright, без «напишите селектор».

Второй мотив — диплом. Нужен работающий продукт, измеримый эксперимент и новизна, которую можно защитить словами.

## 2. Что уже есть

| Репозиторий | Что это | Судьба |
|---|---|---|
| natl | язык, интерпретатор, адаптеры, CLI, агент. API 1.0 заморожен, пакеты в npm | ядро, остаётся |
| testblox | Electron + React, v1.1.0, свой JSON-формат и свой раннер | становится UI, код частично переписывается |
| testblox-runner | CLI под JSON-формат | выбрасывается, его роль играет `@natl/cli` |
| testblox-mcp | MCP-сервер над старым workspace | вторая волна, переписывается на natl |

Строим не с нуля. Сводим четыре репозитория в одну систему и удаляем дубли.

## 3. Цели

1. Один формат тестов — NATL YAML в репозитории пользователя.
2. Запись кликов в браузере превращается в YAML без ручного кода.
3. Прогон и пошаговый просмотр внутри приложения: шаг → скриншот → что изменилось.
4. Те же тесты в CI без приложения: `natl run`, отчёт JUnit.
5. Один ИИ-компонент для всех генераций: из diff, из страницы, из OpenAPI.
6. Сборки: Windows и Linux. macOS — цель сборки в CI без подписи.

## 4. Не-цели

- TMS, облако, аккаунты, командные дашборды.
- Расширение браузера как основная форма (третья волна).
- iframe, новые вкладки, загрузка файлов (языковая волна 6+ в natl).
- Мобильные приложения и desktop-приложения как объект тестирования.
- Подпись и нотаризация сборок под macOS.

## 5. Анти-цели

Любой пункт ниже означает, что мы вернулись к состоянию «четыре репозитория»:

- второй формат тестов рядом с YAML;
- второй раннер рядом с `natl run`;
- хранение тестов вне репозитория пользователя.

## 6. Ограничения

- Один разработчик, диплом, ограниченный срок.
- Разработка на Windows. Linux проверяется в CI, macOS — только сборкой.
- Electron отвечает за GUI, Docker — только за headless-прогон. Одно из другого не следует.
- Продукт для простых приложений: формы, вход, регистрация, CRUD, оплата. Сложные SPA с iframe и WebSocket — за пределами обещаний.

## 7. Рассмотренные подходы

| Подход | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| A. Electron-приложение | код UI уже есть; установщики работают; окно для «Postman для UI» | 200 МБ, только Windows, отдельный браузер для записи | выбран |
| B. Локальное веб-приложение | нет установки, кроссплатформенно | нет «рабочего стола», запись требует отдельного браузера и сервера | отклонён |
| C. Расширение браузера | запись в настоящей сессии, ноль установки | нет окна с историей и просмотром; MV3, разрешения, проигрывание хрупкое | отклонён как основная форма |
| D. Гибрид: B, затем обёртка в Electron | один код на всё | два этапа, два браузера на время перехода | отклонён |

Почему A. Postman победил не умением слать запросы, а тем, что дал окно: собрал, отправил, увидел ответ. Расширение такого окна не даёт — попап на 400 пикселей не рабочий стол. Плюс у нас уже есть работающее приложение: переработать существующую систему проще и честнее, чем начать заново.

Формулировка для текста и защиты: **Postman для UI, где каждый шаг показывает, что произошло на экране.** Не «тесты стали воспроизводимыми» — UI-сценарий зависит от состояния, и это надо признавать первым.

## 8. Архитектура

```
apps/desktop            Electron + React — окно, запись, просмотр
  main/                 вызовы движка, файлы, git
  renderer/             интерфейс
        ↓ импорт
@natl/core              парсер, интерпретатор, отчёты
@natl/adapter-*         playwright | selenium | cypress (движки)
@natl/agent             единый генератор YAML из контекста
@natl/cli               natl run — тот же движок без GUI
docker/                 образ с браузерами для CI
```

Поток данных один:

```
запись кликов → YAML в репозитории → runNatlFile → JsonReporter → экран прогона
                                      ↑
                            тот же путь в CI: natl run
```

`runNatlFile` — стабильный экспорт `@natl/core` (см. [`core/docs/api-1.0.md`](https://github.com/arslan-ahmetjanov/natl/blob/main/core/docs/api-1.0.md)). Приложение вызывает его прямо из main-процесса, без дочерних процессов и без второго раннера. Отчёт берём из `JsonReporter`, скриншоты и трассы — из артефактов адаптера.

## 9. Что делаем с четырьмя репозиториями

| Что | Решение |
|---|---|
| `testblox/electron/store/filestore.js` | выбросить. Данные — YAML-файлы в папке пользователя |
| `testblox/electron/services/playwrightRunner.js` | выбросить. Заменяется на `runNatlFile` |
| `testblox/electron/services/apiRunner.js` | выбросить. В natl есть `httpRequest` и `with: http` |
| `testblox/electron/services/pageParser.js` | оставить. Селекторы нужны и рекордеру, и обходу сайта |
| `testblox/electron/services/swaggerParser.js` | оставить, переносится в единый ИИ-модуль |
| `testblox/electron/services/llmGenerateTests.js` | выбросить. Вход в `@natl/agent` |
| `testblox/frontend/src/screens/*` | оставить 4 экрана (открытие папки, запись, список тестов, прогон), остальные удалить |
| `testblox-runner/*` | выбросить целиком |
| `testblox-mcp/*` | вторая волна, переписать на natl |
| `natl/*` | без изменений в публичном API, добавляем точки расширения |

Историю коммитов сохраняем через `git subtree add`, не через submodules.

## 10. Модель данных

Единственный формат — NATL YAML. Один сценарий — один файл, читается в диффе, ревьюится в PR, запускается в CI.

Миграция старых workspace `.testblox/tests/*.json`: одноразовый скрипт при открытии папки. Что переносится: шаги, переменные, значения из `.env`, страницы как `vars`. Что теряется и о чём сообщаем пользователю: общие шаги (становятся YAML-импортами), regex-переменные (становятся функциями natl), API-bases (становятся `engine: http` сценариями).

Обратной совместимости с JSON не обещаем.

## 11. Запись кликов

Chromium поднимает Playwright в видимом режиме. В страницу внедряется скрипт, который слушает:

- `click` — берёт элемент, строит селектор через `pageParser` (приоритет: `data-testid`, `id`, `name`, `aria-label`, текст);
- `input` / `select` / `change` — записывает `fill` и `select`;
- навигацию — записывает `goto`.

После каждого действия приложение спрашивает: «появился `.toast` — добавить проверку?». Согласился — в YAML попадает `assert`. Отказался — шаг сохраняется без проверки.

Стоп → YAML. Дальше `natl validate`, чтобы файл не был мусором.

Ограничения называем сразу в интерфейсе: iframe, новые вкладки и файловые диалоги не записываются.

## 12. Прогон и просмотр

Тот же экран, что у Postman: список шагов, статус каждого, скриншот до и после, текст ошибки, время.

- зелёный прогон — шаги и тайминги;
- красный — упавший шаг раскрыт, скриншот, сообщение `formatStepFail`;
- история прогонов — папка артефактов, не база.

Повтор одного шага без перезапуска в первую волну не входит: `runNatlFile` поднимает сессию браузера заново, и восстановить состояние между шагами нечем. Вместо этого кнопка «повторить сценарий» — прогон занимает секунды, а обещание «повторить шаг» пришлось бы либо обходить скрытым префиксом, либо хранить снимок состояния. Оба варианта дороже, чем польза.

Скриншоты на каждом шаге ядро не делает: `RunOptions.screenshot` снимает только падение. Обходим без правок ядра — в `RunOptions.adapters` передаётся своя фабрика, которая оборачивает адаптер и снимает кадр до и после каждого действия. Шаги и статусы приходят через `RunOptions.reporter.stepStart` / `stepEnd`, это часть стабильного API.

## 13. Единый ИИ-компонент

Сейчас логика размазана: в natl/agent это «diff → YAML», в testblox — «страница → JSON». Складываем в один модуль.

Вход:

| Источник | Что даёт |
|---|---|
| `diff` | изменение в коде → какие сценарии затронуты |
| `page` | DOM страницы → сценарии для формы и навигации |
| `openapi` | спецификация → сценарии для эндпоинтов |

Выход всегда один: NATL YAML, прошедший `parseNatlDocument`.

Пайплайн уже написан в natl/agent и переносится как есть: промпт → ответ в JSON → детерминированная нормализация → валидация по `natl.test.schema.json` → self-heal при провале. Из testblox добавляются `pageParser` и `swaggerParser` как поставщики контекста.

## 14. Git-native и CI

- Тесты — файлы в репозитории пользователя. Ветки, PR, ревью работают как обычно.
- Агент читает diff PR и предлагает сценарий в том же PR. GitHub Action для natl/agent уже есть (`action.yml`).
- CI не требует приложения: `natl run tests/ --reporter junit`.
- Контейнер для CI: образ на базе `mcr.microsoft.com/playwright` с установленным `@natl/cli`. Это аналог newman, и он уже работает — в дипломе идёт как готовый компонент.

## 16. Границы MVP (волна 1)

Обещание одно, и оно же проверяется на защите:

> **Записал клики — получил YAML-тест, который запускается в приложении и в CI.**

### Входит

1. Открыть папку репозитория.
2. Ввести URL — открывается Chromium.
3. Запись действий: клик, ввод, выбор в списке, переход по ссылке.
4. Стоп — сохраняется `tests/<имя>.yaml`, файл сразу проходит `natl validate`.
5. Прогон в приложении: список шагов, статусы, скриншот до и после, сообщение об ошибке на упавшем шаге.
6. Одна страница документации: как запустить тот же файл в GitHub Actions (`npx @natl/cli run`, JUnit в артефакты). Кода в приложении не требует.

### Не входит и почему

| Что | Почему не сейчас |
|---|---|
| ИИ-генерация новых сценариев | уже написана в `@natl/agent`; подключаем после того, как луп работает |
| Обход сайта и подсказки проверок | без рекордера нечего подсказывать |
| Сценарии `engine: http`, Swagger | другая половина продукта, в MVP не проверяется |
| MCP-сервер | не участвует в срезе «записал → зелёный прогон» |
| Авторизация GitHub, device flow | пуш работает через системный git |
| Сборки под Linux и macOS | для MVP достаточно `npm start` на Windows |
| Миграция старых `.testblox/*.json` | архивация TestBlox 1.1.0 и без миграции |
| Правка YAML на месте | рекордер пишет новый файл, редактора в MVP нет |
| Переменные с regex, общие шаги | в MVP переменные берём из `.env` |
| iframe, новые вкладки, загрузка файлов | языковая волна 6+ в natl, не наша работа |
| Повтор шага, параллельный прогон | прогон занимает секунды |

### Готово, когда

1. На чужом приложении из десяти действий восемь попадают в YAML без ручной правки.
2. Повторный прогон того же файла без правок зелёный два раза подряд.
3. На падении видно шаг, скриншот и текст ошибки — без чтения YAML.
4. `natl run` в терминале даёт тот же результат, что приложение.
5. На чистой машине от запуска до первого зелёного прогона — не больше десяти минут.
6. Демо проходит без интернета: браузер прогрет заранее.

### Правило, которое держит границы

`@natl/core` в MVP не меняем. Если задача требует правки ядра — значит она не для MVP. Единственное исключение: необязательные поля `channel` / `executablePath` в `AdapterFactoryOptions`, они не ломают 1.0.

### Порядок работ

1. Монорепо: `git subtree`, общий pnpm-workspace. Ничего не работает, но дальше всё быстрее.
2. YAML вместо JSON: чтение и запись файлов.
3. Прогон: `runNatlFile` + отчёт на экране.
4. Рекордер.
5. Документация по CI и упаковка для демо.

Пункты 2 и 3 дают работающее приложение без рекордера — это точка, где уже можно показывать прогресс.

Волна 2 — после защиты: обход сайта, ИИ-генерация поверх готового лупа, MCP, device flow, Linux и macOS, миграция старых workspace.

Волна 3 — идеи: `adapter-extension`, чтобы тот же YAML гонялся в браузере пользователя.

## 17. Эксперимент для защиты

Нужны числа, а не «удобно».

Материал: 3–5 простых приложений. Своё, приложение знакомого, сгенерированное моделью по одному промпту.

Метрики:

| Метрика | Как считаем |
|---|---|
| Покрытие записи | доля действий, попавших в YAML без ручной правки |
| Качество селекторов | сколько шагов пережили повторный прогон без правок |
| ИИ: валидность | доля сценариев, прошедших схему с первого ответа |
| ИИ: после self-heal | доля прошедших после починки |
| Время | минуты от открытия приложения до первого прогона |
| CI | прогон тех же тестов в контейнере, совпадение результатов |

Стенд для двух последних строк уже есть в natl: `agent/eval` и `tests/agent-release`.

## 19. Решения по итогам ревью

**События по ходу прогона.** Есть: `RunOptions.reporter` принимает `stepStart` / `stepEnd`, это часть стабильного API 1.0. Живую страницу приложение между шагами не получает: адаптер создаётся и закрывается внутри `runNatlFile`.

**Скриншоты на каждом шаге.** Ядро снимает только падение (`RunOptions.screenshot`). Обходим без правок ядра: в `RunOptions.adapters` передаём свою фабрику, которая оборачивает адаптер и снимает кадр до и после каждого действия. Стоимость — один файл-обёртка вместо доработки интерпретатора.

**Повтор шага.** Не делаем. Восстановить состояние сессии между шагами нечем; скрытый перепрогон префикса — тот же полный запуск. Вместо этого кнопка «повторить сценарий».

**Правка YAML на месте.** Пакет `yaml` уже в зависимостях `@natl/agent`; его Document API сохраняет комментарии и порядок. Рекордер по умолчанию пишет новый файл, «дописать в существующий сценарий» — отдельный шаг после первой волны.

**Согласование версий.** Единый релизный поезд из монорепо: `@natl/*` публикуются одной версией, приложение собирается с workspace-версией ядра, `natl run` в CI ставит ту же версию из npm. Проверка честности — прогон одного и того же сценария приложением и CLI в CI с совпадением результата.

**Браузер в приложении.** Адаптер вызывает `browserType.launch`, то есть нужны браузеры Playwright. В установщик они не влезают — качаем при первом запуске в `userData/ms-playwright` с прогрессом в интерфейсе. Для защиты прогреваем заранее. Дополнительно добавим опциональные `channel` и `executablePath` в `AdapterFactoryOptions` — это новое необязательное поле, 1.0 не ломает.

**Git в приложении.** Уже реализовано в testblox через `simple-git`: открыть папку, статус, дифф, коммит, пуш, ветки, remote. Работает через системный git, токены не хранит. Оставляем.

## 20. Имя и авторизация

Имя продукта — **NATL**, без суффикса. Позиционирование живёт в подзаголовке: «Postman для UI». Папка `apps/desktop` в коде может остаться `testblox`, публично имя не используется. Релизы TestBlox 1.1.0 в тексте диплома становятся разделом «предыдущая версия системы».

Авторизация делится на две задачи:

- **Волна 1:** пуш через системный git. Пользователь уже настроил SSH или credential manager, токены мы не храним. Для «Git-native» этого достаточно: файлы в репозитории, дифф, PR, агент на PR в CI.
- **Волна 2:** device flow GitHub. Приложение показывает код, пользователь подтверждает в браузере, секрет клиента не вшивается. Токен — в Windows Credential Manager. Нужен для создания репозитория и PR из приложения.

Если тема диплома прямо требует «интеграцию с GitHub», порядок меняется: device flow переезжает в волну 1.
