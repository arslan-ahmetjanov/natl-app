# Формат проекта

Документ описывает папку проекта NATL IDE как контракт: где лежат файлы, что в них пишется, что считается ломающим изменением. Рассчитан на человека, который пишет сценарий и ресурсы, не открывая исходники приложения.

Сверено с приложением 0.9.6. Что осталось до 1.0.0 — в [`roadmap-1.0.md`](./roadmap-1.0.md).

## Что это

Проект — обычная папка на диске. Сценарии и ресурсы лежат в ней файлами, базы данных нет: папка и есть хранилище (`apps/desktop/electron/natl/store.js`).

Проект рассчитан на git. Сценарии — текстовые файлы, их видно в диффе, приложение умеет коммитить.

YAML правится двумя способами: руками в любом редакторе и в приложении. Оба способа дают один и тот же файл, приложение ничего не хранит у себя.

Приложение работает только внутри открытой папки: пути наружу отклоняются (`run.js`, `resources.js`).

## Структура папки

```
моя-папка/
  tests/
    login.yaml
  pages/
    login.yaml
  artifacts/                    # появляется после первого прогона
    natl/
      2026-11-14T09-12-33-123Z/
        step-1-before.png
        step-1-after.png
  .testblox/                    # служебное, создаёт приложение
  .env
  .gitignore
  natl.config.yaml              # необязательный
```

| Путь | Кто создаёт | Правится руками | Назначение |
|---|---|---|---|
| `tests/` | приложение при открытии папки | да | сценарии, можно раскладывать по подпапкам |
| `pages/` | приложение | да | ресурсы (page objects) |
| `artifacts/` | приложение при прогоне | нет | кадры прогонов |
| `.testblox/` | приложение | нет | настройки рабочей папки: `workspace.json`, `actions.json`, `sharedSteps.json` |
| `endpoints/`, `apiBases/` | приложение | — | пустые папки старой модели, формат их не использует |
| `.env` | приложение (заголовок) | да | значения для `$env` и `$secret` |
| `.gitignore` | приложение дописывает | да | добавляет `reports/`, `.env`, `.env.local` |
| `natl.config.yaml` | человек | да | настройки движка на весь проект |
| `<файл>.bak` | приложение | нет | прошлая версия после сохранения битого YAML |

Что внутри:

- `tests/` читается рекурсивно, расширения `.yaml` и `.yml`. Приложение пропускает скрытые файлы (с точки), `node_modules` и `artifacts` (`store.js`).
- `pages/` читается без подпапок: ресурсы кладутся в корень папки (`resources.js`).
- `artifacts/` в список сценариев не попадает и в `.gitignore` автоматически не добавляется. Если кадры не нужны в репозитории, добавьте `artifacts/` сами.
- `.testblox/` на сценарии не влияет. Коммитить его не обязательно: при открытии папки приложение создаст служебные файлы заново.
- `natl.config.yaml` читает движок, приложение его не пишет и не показывает. Поля и приоритеты — в `@natl/core/docs/syntax.md`, раздел «Project config». Приложение всегда передаёт движку свою папку артефактов, поэтому `artifacts_dir` из конфига в нём не действует.
- `<файл>.bak` появляется, когда приложение сохраняет текст, который не разбирается как YAML. В списке сценариев `.bak` не виден (`ipc/natl.js`).

## Сценарий (tests/)

### Минимальный пример

```yaml
name: Login smoke
engine: playwright
vars:
  base_url: https://example.com
steps:
  - goto: $base_url
  - fill: "#email"
    with: demo@example.com
  - click: "#login-btn"
  - assert: ".welcome"
    text: "Welcome"
```

### Поля

| Поле | Обязательное | Кто читает | Комментарий |
|---|---|---|---|
| `name` | нет | движок, список, отчёт | без него берётся имя файла (`lint.js`, `scenario.js`) |
| `engine` | нет | движок | по умолчанию `playwright` (`config.ts`) |
| `vars` | нет | движок | подстановки `$имя`; приложение пишет сюда `base_url` |
| `steps` | да для сценария | движок | список шагов; ресурс может жить на одних `actions` |
| `imports` | нет | движок | список файлов ресурсов |
| `secrets` | нет | движок | откуда брать `.env` |
| `tags` | нет | движок, CLI | выбор подмножества сценариев в CLI |
| `timeout`, `retries` | нет | движок | таймаут шага, повторы прогона |
| `data`, `cases`, `before_each`, `after_each` | нет | движок | данные и хуки, интерфейс их не показывает |
| `actions`, `elements`, `locator_strategy` | нет | движок | нужны файлу ресурса; в сценарии тоже допустимы |

Приложение само пишет только `name`, `engine`, `vars`, `steps` (`convert.js`, `recorder.js`). Проверка до запуска смотрит на `name`, на наличие `steps` или `actions`, на глаголы и на `with` у `fill` и `select` (`lint.js`).

### Шаги

| Глаголы | Движок | Проверка приложения | Приложение пишет |
|---|---|---|---|
| `goto` | да | да | да |
| `click`, `tap` | да, `tap` — синоним | да | да для `click` |
| `fill`, `select` | да | да, требует `with` | да |
| `check`, `uncheck` | да | да | да |
| `wait` | да | да | да |
| `assert` | да | да | да |
| `screenshot` | да | да | да |
| `log` | да | да | да |
| `get`, `post`, `put`, `patch`, `delete` | да | да | да, через диалог шага |
| `set`, `scroll`, `swipe`, `long_press` | да | да | нет |
| `do`, `include` | да | да | нет |
| `if`, `for`, `repeat`, `parallel`, `with` | да | да | нет |
| `soft_assert`, `api`, `get_text`, `get_attr`, `debug` | да | нет, предупреждение | нет |

Три ограничения проверки:

1. Все ключи шага считаются глаголами. Поэтому `text:`, `visible:`, `state:`, `save:`, `user:` дают предупреждение «неизвестный глагол». Это ложное срабатывание: движок читает их как обычные поля шага (`lint.js`, `parser.ts`). Пример выше проходит проверку с одним таким предупреждением про `text`.
2. Глагол вне списка движка до запуска только предупреждает. Прогон упадёт с ошибкой «Unknown step» (`parser.ts`).
3. Вложенные шаги (`then`, `else`, `steps` внутри `if`, `for`, `repeat`, `parallel`, `with`) проверка не смотрит.

Чего приложение не умеет: запускать сценарии с `engine`, отличным от `playwright` (зарегистрирован один адаптер, `run.js`), предлагать в диалоге шага `do`, `include`, жесты и `soft_assert`, показывать `tags`, `cases`, `timeout` и `retries`.

### Переменные и секреты

`vars:` задаёт значения прямо в файле. `$env.NAME` и `$secret.NAME` берутся из `.env` или из окружения процесса.

Движок ищет `.env` рядом со сценарием (то есть `tests/.env`) и в рабочем каталоге процесса (`secrets.ts`). `.env` в корне проекта сам не подхватывается, хотя приложение создаёт его именно там. Если значения лежат в корне, укажите файл явно:

```yaml
secrets:
  env:
    file: ../.env
```

## Ресурсы (pages/)

Ресурс — тот же YAML, что читает движок: page object с локаторами и переиспользуемыми действиями. Отдельного формата нет (`resources.js`).

```yaml
locator_strategy: css
elements:
  email: "#email"
  password: "#password"
  login_button: "#login-btn"

actions:
  login:
    - fill: $email
      with: $user
    - fill: $password
      with: $pass
    - click: $login_button
```

- `elements` — имя и селектор. Селектор пишется строкой или объектом `{ strategy, value }`. Имя становится переменной: в шагах работает `$email` (`interpreter.ts`, `locator.ts`).
- `locator_strategy` на корне файла задаёт стратегию для строковых селекторов. Порядок: стратегия элемента, затем файла, затем `natl.config.yaml`, затем `css` (`syntax.md`).
- `actions` — имя и список шагов. Шаги те же, что в сценарии.
- Ресурс из одних `elements` приложение не проверяет и не запускает. Если вставить его текст в проверку сценария, она скажет «Нет ни steps, ни actions» (`lint.js`).

### Как сценарий ссылается на ресурс

Ссылка состоит из двух частей: подключение файла (`imports`, верхний уровень) и вызов действия (`do:` внутри `steps`). Ниже фрагмент, полный сценарий — в разделе «Пример с нуля».

```yaml
imports:
  - ../pages/login.yaml

steps:
  - goto: $base_url
  - do: login.login
    user: $user
    pass: $pass
  - assert: ".welcome"
    text: "Welcome, demo"
```

- `imports` — путь относительно файла сценария. Из `tests/` рабочий вид: `../pages/login.yaml`. Движок дополнительно ищет файл в `<папка сценария>/pages/` и `../pages/` (`parser.ts`, `resolveImportPath`), но явный путь понятнее.
- `do: <страница>.<действие>` вызывает действие. Короткая запись `do: <действие>` работает, если имя действия уникально среди импортов (`interpreter.ts`).
- Соседние ключи у `do:` (`user:`, `pass:`) движок передаёт в область действия на время вызова.
- Элементы импортированного файла доступны в сценарии по имени: `$email`.
- Имя страницы движок берёт из поля `name` без слова `Page` и в нижнем регистре, а если `name` нет — из имени файла. Кнопка «В сценарий» в приложении строит `do:` из имени файла. Поэтому либо не задавайте `name` в ресурсе, либо пишите его одним словом латиницей: `<Файл>Page`. Иначе `do:` и страница не совпадут.

Отдельное расхождение: кнопка «В сценарий» подставляет путь от сценария,
`../pages/<файл>.yaml` (`ResourcesScreen.jsx`). Если сценарий лежит в подпапке
`tests/`, поднимитесь на уровень выше: `../../pages/<файл>.yaml`.

## Артефакты

Каждый прогон получает свою папку: `artifacts/natl/<метка времени>/`, метка — ISO-время, где двоеточия и точки заменены на дефис (`run.js`).

Кадры пишет обёртка вокруг адаптера: перед действием и после него.

| Файл | Когда появляется |
|---|---|
| `step-N-before.png` | перед действием номер N |
| `step-N-after.png` | после действия номер N |

- `N` — счётчик действий адаптера за весь прогон, а не номер шага в YAML. Действия внутри `do:` дают каждый свой кадр, сам шаг `do:` — нет.
- Кадры дают `goto`, `click`, `fill`, `select`, `check`, `uncheck`, `wait`, `scroll`, `swipe`, `long_press` (`run.js`, `ACTION_METHODS`). `assert`, `screenshot`, `get_text` кадров не дают.
- Ошибка скриншота не валит шаг: кадр просто не появляется.
- Движок кладёт в эту же папку своё: `<метка>-<имя>.png` при падении, `<метка>-<имя>.zip` для трассы и `<метка>-<имя>.webm` для видео (`interpreter.ts`, `adapter-playwright`). Трасса по умолчанию пишется только при падении.
- Очистка удаляет каталоги верхнего уровня внутри `artifacts/`, то есть в текущей раскладке всю папку `artifacts/natl` (`artifacts.js`). `keepLast` считает каталоги верхнего уровня, а не прогоны. Приложение вызывает очистку с нулём, то есть удаляет всё. Автоматической очистки нет: кадры копятся, пока их не удалить кнопкой.

## Правила имён

Приложение строит имя файла из названия: нижний регистр, всё кроме латиницы, кириллицы и цифр заменяется на дефис, дефисы по краям срезаются, пустое имя становится `scenario`, занятое получает `-2`, `-3` (`store.js`, функция `scenarioFileName`). Ресурсы именуются так же (`resources.js`).

Правила для файлов, которые пишете руками:

- Только `.yaml` или `.yml`. Приложение всегда создаёт `.yaml` и при переименовании тоже ставит `.yaml`.
- Не начинайте имя сценария с точки: такие файлы приложение пропускает, сценарий исчезнет из списка.
- Без пробелов, `..` и разделителей пути. Кириллица допустима, но латиница надёжнее: имя файла ресурса попадает в `do:`.
- Windows запрещает имена `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, точку и пробел в конце.
- `Login.yaml` и `login.yaml` на Windows и в git — один файл.

Переменные и имена элементов: латиница, цифры и `_`, первый символ — буква или `_`. Ссылка `$имя` распознаётся только в таком виде (`expr.ts`, `locator.ts`). Теги — строки, регистр учитывается, выбор по тегам делает CLI (флаг `--tags`).

## Совместимость

### Ломающие изменения

| Изменение | Почему ломает |
|---|---|
| переименовать или удалить поле корня | старый файл перестанет читаться так, как задумано |
| сделать необязательное поле обязательным | файлы без него перестанут запускаться |
| изменить смысл шага или глагола | старый файл начнёт делать не то |
| удалить глагол | файлы с ним упадут на «Unknown step» |
| переименовать `tests/`, `pages/`, `artifacts/` или поменять их роль | сломаются пути у всех проектов |
| изменить правила поиска `imports` или адресации `do:` | сломаются ссылки между файлами |
| изменить смысл полей `name`, `vars`, `elements` | сломаются существующие ресурсы |

### Не ломающие изменения

- новое необязательное поле: старый файл его не содержит, поведение не меняется;
- новый глагол: старые файлы его не используют;
- новая форма записи элемента или шага при поддержке старой;
- новое предупреждение проверки: ошибкой не считается;
- новая раскладка внутри `artifacts/`, если сценарии и запуск не меняются. Для тех, кто читает кадры снаружи, это всё же изменение: предупредите в CHANGELOG.

### Как читаются старые и дефектные файлы

- Неизвестное поле в корне движок отбрасывает, ошибки нет (`parser.ts`, схема допускает лишние поля). Исключение — `secrets`: он описан строго.
- Неизвестный глагол: проверка в приложении предупреждает, прогон падает с «Unknown step» (`parser.ts`).
- Битый YAML: в списке появляется строка с пометкой «ошибка», файл открывается как текст, проверка пишет «YAML не разбирается» (`scenario.js`, `lint.js`). При сохранении битого текста приложение всё равно пишет файл, а прошлую версию кладёт в `<файл>.bak` (`ipc/natl.js`).
- Файл без `name`: в списке и отчёте используется имя файла.
- Файл без `steps` и `actions`: проверка выдаёт ошибку, прогон проходит без шагов.

### Версия формата

Поля с версией нет: ни в сценарии, ни в папке. Приложение определяет проект по наличию `.testblox/workspace.json`, а формат файла — по расширению. Значит, отличить «формат 1.0» от «формата 0.9» по файлу нельзя.

Предлагаемое правило: с выпуском 1.0.0 формат 1.0 заморожен. Файлы, созданные в 1.0.0, читаются и запускаются во всей линейке 1.x. Всё из таблицы ломающих изменений — только в 2.0. До 1.0.0 ломающие правки допустимы, но каждая описывается в CHANGELOG.

## Пример с нуля

1. Создайте пустую папку `login-demo` и откройте её в приложении. Появятся `tests/`, `pages/`, `endpoints/`, `apiBases/`, `.testblox/`, файл `.env`; в `.gitignore` допишутся служебные строки.
2. Создайте файл `tests/login.yaml` с минимальным сценарием из раздела «Сценарий» и подставьте свой адрес вместо `https://example.com`.
3. Нажмите «Запустить». После прогона появится `artifacts/natl/<метка времени>/` с кадрами, результат — в панели прогона.
4. Создайте `pages/login.yaml`: вкладка «Окружение», кнопка создания файла, либо просто новый файл с примером из раздела «Ресурсы».
5. Перепишите `tests/login.yaml` так, чтобы шаги шли через ресурс:

```yaml
name: Login smoke
engine: playwright
imports:
  - ../pages/login.yaml
vars:
  base_url: https://example.com
  user: demo@example.com
  pass: secret

steps:
  - goto: $base_url
  - do: login.login
    user: $user
    pass: $pass
  - assert: ".welcome"
    text: "Welcome, demo"
```

6. Сохраните и запустите снова. Три шага с `fill` и `click` теперь живут в одном действии `login`, и то же действие можно вызвать из другого сценария.

## Чек-лист

1. Файл лежит в `tests/` (сценарий) или в корне `pages/` (ресурс), расширение `.yaml`, имя без пробелов и без точки в начале.
2. У сценария есть `steps`, у ресурса — `elements` и `actions`. Поле `name` не обязательно, но с ним отчёт читаемее.
3. Каждый шаг — объект с одним глаголом из таблицы; у `fill` и `select` есть `with`.
4. `imports` указывает на `../pages/<файл>.yaml`, а `do:` совпадает с именем страницы: именем файла или `name` без слова `Page`.
5. Все `$переменные` и `$элементы` объявлены: в `vars`, в `elements` или в `.env`.
6. В проекте нет второго файла с тем же именем в другом регистре, и `artifacts/` не попал в коммит, если кадры не нужны.
7. Прогон зелёный, кадры появились в `artifacts/natl/<метка>/`, в списке сценариев нет пометки «ошибка».
